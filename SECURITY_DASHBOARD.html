🎯 What it does

Centralizes Shift Rostering, Task Management, Ticketing, OEM Case tracking, a two-vault (Team + Personal) encrypted Password Manager, and multi-format (CSV/HTML/PDF) Reports for an internal ops/security team, with role-based UI (Admin vs. Member) backed by database-level RLS enforcement.

⚡ Architectural Bet

No custom backend, no Service Role key, ever (ADR-008) — every authorization decision is enforced by Postgres RLS policies, not application code the client could bypass. The one exception, added in Phase 12, is a single narrow server route that verifies a Supabase session before proxying to an AI API — deliberately kept as the only server-side surface in the app.

Governance

Methodology & Data Integrity

This dashboard's policy on what a score is allowed to mean, and the per-module audit trail behind every number shown above. See .claude/commands/security-audit.md ("Rule: no fabricated or unrealistic scores") for the source-of-truth rule text this section implements.

No fabricated or unrealistic scores — the policy

  • Every percentage, status, or score on this page resolves to a specific tool output, a specific file:line citation, or the literal status "Not yet verified" — never a guessed number presented as fact.
  • "Not yet verified" is excluded from every average, not counted for or against it.
  • Scores are never rounded up to look better than the underlying evidence supports.
  • Every composite score shows its formula and inputs inline (see the Security Score breakdown on Overview) so it can be recomputed by hand from this run's data.
  • All scores are computed live from this run's data arrays — never hand-typed constants carried over from a previous run.
  • Any score that changes between runs must have an explainable cause (new evidence, code change, tool re-run) — an unexplained delta is treated as an audit bug, not a fact.
